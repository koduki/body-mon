# アーキテクチャ判断記録

## Health Connectを正本とする

センサー・ベンダーアプリの生データはHealth Connectに残し、アプリ独自DBへは表示・比較に必要な集計値と直近の運動セッションだけを保存する。これにより、同じ歩数を複数ソースから二重加算する問題と、健康ログの不要な複製を避ける。

## Roomを使う理由

Health Connectを画面描画のたびに読むと、権限・ページング・集計・レート制御がUIへ漏れる。Roomを読取りモデルとして置き、履歴読取り権限がある初回同期では90日、その後の起動時・手動操作・許可されたバックグラウンド処理では28日を再集計する。BigQueryは使わない。

運動セッションは同期範囲だけを削除・再作成し、90日バックフィル後の古い履歴を
28日同期で消さない。

## Geminiへ全データを渡さない

Geminiには次のローカル関数だけを公開する。

- `get_body_composition`
- `get_activity_summary`
- `get_exercise_summary`
- `get_sleep_summary`
- `get_heart_rate_summary`
- `get_activity_intensity_summary`
- `get_metabolism_summary`
- `get_nutrition_summary`
- `get_goal_progress`

Geminiが質問に必要な関数と期間を返し、AndroidアプリがRoomを問い合わせて加工済みJSONを返す。生レコード、位置情報、内部IDは渡さない。

## 会話メモリー

チャット画面とGeminiへ渡す文脈は同じ直近20件に揃える。利用者発言6件ごと、および
週次分析の直前に、食事・睡眠・運動・仕事・生活リズム・好み・制約を中心とした長期要約
へ更新する。アシスタントの提案は習慣として記録しない。要約済みかつ直近20件より古い
本文はRoomから削除し、長いログで画面が埋まることを防ぐ。未要約の行は削除しない。
長期要約は設定画面で参照でき、チャット上には出さない。誤要約の手動訂正は当面しない。

## チャット添付

AndroidのStorage Access Frameworkで利用者が明示選択した写真、PDF、テキスト文書だけを
読み取るため、ストレージ全体への権限は要求しない。添付はGemini `generateContent`の
`inlineData`として現在の利用者ターンにだけ含める。20MBのインラインリクエスト上限へ
余裕を残すため、1ファイル10MB、最大4件、rawデータ合計12MBに制限する。

添付本体はRoomや内部ストレージへ永続化しない。Roomの会話には表示用ファイル名だけを
保存し、次のターンへ本体を暗黙に再送しない。添付を直接参照する追加質問では再添付が必要。

## 任意のHealth Connect指標

体重・体脂肪・歩数・距離・運動・活動消費を必須権限とし、睡眠・心拍・基礎代謝・活動強度・栄養を任意権限とする。任意項目の権限拒否や端末非対応があっても既存同期は継続する。活動強度は`FEATURE_ACTIVITY_INTENSITY`を実行時に確認する。

履歴読取りは`FEATURE_READ_HEALTH_DATA_HISTORY`を実行時に確認し、利用可能な場合だけ
権限を要求する。

栄養はあすけんがHealth Connectへ書き出す摂取カロリー・たんぱく質・脂質・炭水化物を
日次集計する。ビタミンや食塩相当量など、あすけんが書き出さない栄養素は取得しない。

食事回数は`NutritionRecord`のstart/endで近いレコードを1食にまとめて数える。詳細は
[食事回数はNutritionRecordのstart/endでまとめる](#食事回数はnutritionrecordのstartendでまとめる) を参照する。

Roomはv7。v3で主睡眠の開始・終了、睡眠中心拍、減量開始日を、v4でチャット添付の
表示用ファイル名を、v5で朝の5分ルーティン時間を、v6で摂取カロリーとPFCを、
v7で食事回数と食事クラスタを追加し、
`ALTER TABLE`移行で目標・会話・既存集計を保持する。v6移行直後の栄養値は空だが、
次の通常同期で直近28日（履歴初回は最大90日）をHealth Connectから再集計する。

## KPIを保存する理由

UIとGeminiが同じ定義を使うため、端末内の`WeeklyReportBuilder`が7日中央値、
28日Theil–Sen傾向、朝トレ実施日数、歩数維持、回復、測定品質を一度だけ計算し、
シリアライズした週次スナップショットを保存する。計算式と科学的根拠は
[`KPI_DESIGN.md`](KPI_DESIGN.md)を正本とする。

追加した週次ダッシュボードKPIは端末内表示専用とし、新しいGemini関数では公開しない。
手動週次AI分析も`existingAiContract()`で従来の週報項目だけを再構成し、KPI追加に
伴って外部送信項目が暗黙に増えないようにする。減量開始日もAIペイロードから除外する。
一方、あすけん由来の摂取カロリーとPFCはHealth Connectの栄養記録そのものなので、
週次分析の送信契約と自由質問の`get_nutrition_summary`の両方で公開する。
PFCはグラムとエネルギー比を送り、週次AI分析はカロリー収支比較と体重推移を軸に、
低脂質ダイエットの観点で食事・運動量・摂取バランスを扱う。推定エネルギー収支は
デバイス消費量との差であり、端末内表示専用とする。週報画面では推定収支を体重傾向と
対照し、端末内の専門家判定へも載せるが、Geminiの送信契約には追加しない。
一方、自由質問で既存の`get_exercise_summary`が選ばれた場合は、運動データの一部として
朝トレ時間と`morning_routine`分類を返し、朝トレと通常の筋トレを混同させない。

## 食事回数はNutritionRecordのstart/endでまとめる

アプリの同期時刻や`lastModifiedTime`は食事回数に使わない。食事の区切りは
Health Connectの`NutritionRecord.startTime` / `endTime`だけを見る。

- 開始時刻が45分以内、または区間が重なるレコードを1食にまとめる
- 既知の`mealType`（朝・昼・夕・間食）が異なるレコードは、時刻が近くても別の1食とする
- 区間が12時間以上でも、`mealType`が付いているレコードは日次合計にせず食事ラベルを使う
- 同じ日に日次合計と食事単位が混在する場合は、食事単位だけを残す
- `mealType`があれば朝・昼・夕・間食に使い、不明なら開始時刻の時間帯で付ける
- 1日の摂取カロリーとPFCは従来どおりHealth Connectの集計APIを正本にする
- 食事ごとのPFCはクラスタ内のグラムとカロリーを合算する

低脂質ダイエットの運用目安で、食事ごとと1日のPFCを判定する。

| 判定 | 条件 |
|---|---|
| 目安内 | 脂質エネルギー比15〜25%、かつたんぱく質エネルギー比15%以上 |
| 脂質多め | 脂質エネルギー比30%超 |
| 脂質やや多め | 脂質エネルギー比25%超〜30% |
| 脂質少なめ | 脂質エネルギー比15%未満 |
| たんぱく質少なめ | たんぱく質エネルギー比15%未満 |
| 判定保留 | カロリーまたはPFCが欠けている |

画面では積み上げ棒グラフで構成比を出し、今日・推移・週報で確認する。
食事回数と食事ごとの内訳は端末内表示用で、Geminiの送信契約には追加しない。

## 専門コーチを端末内で合成する

長いプロンプトだけに健康判断を任せず、`CoachAssessmentEngine`が週次KPIを
「順調・要観察・調整推奨・判定保留」と根拠、最大2件の行動へ変換する。
Geminiは従来の送信契約で応答し、その後に`CoachResponseComposer`が端末内判定を
合成する。これにより、判定ロジックをJUnitで検証し、新規KPIやコーチシグナルを
外部送信せずに専門性と一貫性を追加する。

自由チャットと週次分析は共通の
`BodyRecompositionCoachPolicy`をsystem instructionへ含める。筋力維持を減量速度より
優先し、観測・解釈・提案を分け、行動を最大2件に絞る。詳細は
[`COACH_POLICY.md`](COACH_POLICY.md)を参照する。

## 直接APIキー方式

完全個人利用のため、利用者本人が入力したGemini APIキーをAndroid Keystoreで暗号化する。コードにはキーを含めない。一般配布へ移行する場合、この判断は無効となり、認証付きバックエンドが必要になる。
