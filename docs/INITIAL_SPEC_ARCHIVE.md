# Health Connect パーソナル健康コーチ MVP仕様書

> 初期検討時のアーカイブです。実装対象の確定仕様は
> [`MVP_SPEC.md`](MVP_SPEC.md) を参照してください。

## 1. 概要

Android端末上のGoogle Health Connectから身体組成・歩数・運動・活動消費カロリーを取得し、端末内で集計・可視化する個人用アプリ。必要なときだけ、利用者が設定したLLM APIへ最小化済みの週次サマリを送信し、ダイエット継続のための助言を受け取る。

本MVPは、単一利用者・単一Android端末・アカウントなしを前提とする。Health Connectの生データとアプリの履歴は端末内に保持し、アプリ運営者用のバックエンドおよびクラウドDBは持たない。

## 2. 目的と成功条件

### 2.1 目的

- 体重だけでなく、体脂肪量と除脂肪量の推移を中心にダイエット状況を把握できるようにする。
- 歩数、運動量、活動消費カロリーを同じ画面で確認し、日々の活動と体組成の変化を結びつける。
- 数字だけでは分かりづらい週次の変化を、過度な断定をしないコーチング文として提示する。
- 健康データの生ログを外部サービスへ恒久保存しない。

### 2.2 成功条件

- 対応データをHealth Connectから読み込み、端末内で日次・週次推移を表示できる。
- 体脂肪量（kg）と除脂肪量（kg）を体重とは別の指標として表示できる。
- 歩数、運動セッション、活動消費カロリーを日次および週次で確認できる。
- LLM分析を有効化した場合でも、生ログではなく集計済みの特徴量だけを送信できる。

## 3. スコープ

### 3.1 MVPに含めるもの

- Health Connectとの連携、利用可能性確認、権限取得・管理導線
- 体重、体脂肪率、除脂肪量、歩数、距離、運動セッション、活動消費カロリーの読取り
- 日次集計および直近7日・28日のトレンド表示
- ダッシュボード、体組成詳細、活動詳細、週次アドバイス、設定画面
- Health Connectのデータ変更を考慮した端末内再集計
- 利用者が入力したLLM APIキーによる任意の週次分析
- ローカル通知による週次レポートの案内

### 3.2 MVPに含めないもの

- ユーザーアカウント、複数端末同期、クラウドバックアップ
- 食事記録・摂取カロリーの入力、バーコード読取り
- 独自の歩数・心拍・GPSの計測やHealth Connectへの書込み
- 医療診断、疾病リスク判定、治療・服薬・食事療法の指示
- iOS版、Wear OS専用アプリ、家族・コーチとの共有
- 骨格筋量の直接表示。Health Connect標準の`LeanBodyMass`は除脂肪量であり、骨格筋量そのものではない。

## 4. 前提と設計原則

1. **Health Connectを生データの正本とする。** アプリは原則読取り専用とし、原記録を複製・再配信しない。
2. **アプリのローカルDBには集計値を保存する。** 表示の高速化、過去トレンド、再権限付与後の継続性のためであり、生の心拍・位置・睡眠ステージ等は保存しない。
3. **LLMへの送信は明示操作または利用者がONにした週次処理に限る。** APIキー・健康データをクラウドDBに保存しない。
4. **助言生成と数値計算を分離する。** 変化量、移動平均、閾値判定は決定的ロジックで算出し、LLMは説明と優先順位付けに限定する。
5. **データの欠損と計測誤差をUI・助言へ反映する。** 体組成計のBIA値は水分や測定時刻で変動するため、日単位の増減を断定しない。

## 5. 技術構成

| 領域 | 採用案 | 備考 |
|---|---|---|
| クライアント | Androidネイティブ、Kotlin、Jetpack Compose | Health Connect APIを直接扱うためネイティブ実装とする。 |
| 最低OS | Android 9（API 28） | Health Connectが利用可能な最小範囲に合わせる。 |
| Health連携 | `androidx.health.connect:connect-client` | 実装時点の安定版を採用する。 |
| 非同期・定期処理 | Kotlin Coroutines、WorkManager | 実行時刻の厳密性ではなく、日次のベストエフォート同期を行う。 |
| 端末内DB | Room | 日別集計・設定・分析履歴のみを格納する。 |
| 秘密情報 | Android Keystore + EncryptedSharedPreferences相当 | LLM APIキーを暗号化保存する。 |
| 通知 | Androidローカル通知 | サーバー/FCMを使わない。 |
| LLM | 利用者自身のAPIキーで直接呼出し | 外部LLMは設定から任意に有効化する。 |

## 6. 取得データと権限

### 6.1 必須データ

| ユーザー表示 | Health Connectレコード | 権限 | 集計・扱い |
|---|---|---|---|
| 体重 | `WeightRecord` | `READ_WEIGHT` | 当日最後の有効測定値を採用する。 |
| 体脂肪率 | `BodyFatRecord` | `READ_BODY_FAT` | 当日最後の有効測定値を採用する。 |
| 除脂肪量 | `LeanBodyMassRecord` | `READ_LEAN_BODY_MASS` | 提供される場合に優先表示する。 |
| 歩数 | `StepsRecord` | `READ_STEPS` | `aggregate()`で日次合計を取得する。 |
| 距離 | `DistanceRecord` | `READ_DISTANCE` | `aggregate()`で日次合計を取得する。 |
| 運動 | `ExerciseSessionRecord` | `READ_EXERCISE` | 種目・開始終了時刻・時間を取得する。 |
| 活動消費 | `ActiveCaloriesBurnedRecord` | `READ_ACTIVE_CALORIES_BURNED` | `aggregate()`で日次合計を取得する。 |

### 6.2 任意データ（MVPでは権限要求しない）

- 睡眠、安静時心拍、基礎代謝、総消費カロリー
- これらは、体組成と運動のMVPが安定後に「回復」または「参考情報」機能として追加する。
- 総消費カロリーはデータ提供元ごとの差が大きいため、MVPでは活動消費カロリーを主指標とする。

### 6.3 権限のUX

- 初回起動時に全権限を一括要求せず、オンボーディングで「体組成」「日常活動」「運動」の価値を説明してから要求する。
- 拒否・一部許可でもアプリを起動可能にし、取得できない指標には理由と再設定導線を表示する。
- 設定画面からHealth Connectの権限管理画面を開けるようにする。
- バックグラウンド読取り権限と履歴読取り権限は初期リリースでは要求しない。通常のアプリ起動時および明示同期で最新データを読む。

## 7. データ処理

### 7.1 体組成

1. 日付ごとに体重・体脂肪率・除脂肪量の最新測定値を取得する。
2. 体重と体脂肪率の計測時刻が近い場合（原則10分以内）に、`脂肪量 = 体重 × 体脂肪率 / 100` を算出する。
3. 除脂肪量は、`LeanBodyMassRecord`が同一時点にあればその値を優先し、なければ `体重 - 脂肪量` を推定値として表示する。
4. 計測時刻が離れている、またはどちらかが欠損している場合は脂肪量を算出せず、「計測不足」と表示する。
5. 体重・脂肪量・除脂肪量は、単日値に加えて7日中央値と前週比を表示する。

### 7.2 日常活動・運動

- 歩数、距離、活動消費カロリーは日付単位の`aggregate()`で取得する。
- 運動セッションは時刻、時間、運動種別を日付単位に集計する。
- 筋力トレーニング、ウェイトリフティング、HIIT等を「筋トレ」として分類し、ウォーキング・ランニング・サイクリング等は有酸素として分類する。
- 複数のデータ提供元がある場合、日次の歩数・距離・活動消費はHealth Connectの集計値を用いる。詳細画面では取得元を表示し、利用者が必要なら集計元を設定で絞れるようにする。

### 7.3 再集計と同期

- アプリ起動時、手動更新時、日次WorkManager実行時に、直近35日を再集計してRoomへupsertする。
- Health Connectの変更トークンをデータ型ごとに保存し、変更が検出された場合も同じ35日再集計を実行する。
- タイムゾーンは端末のローカルタイムゾーンで日付を切る。タイムゾーンが変更された場合は直近35日を再計算する。
- 35日より古い集計済み値はアプリDBに残すが、Health Connectの原データが再読取りできない場合は過去値の訂正を保証しない。

## 8. ローカルデータモデル

### 8.1 `daily_health_summary`

| フィールド | 説明 |
|---|---|
| `date` | ローカル日付（主キー） |
| `steps` / `distance_meters` | 日次の活動量 |
| `active_calories_kcal` | 日次活動消費カロリー |
| `exercise_minutes` | 全運動時間 |
| `strength_minutes` / `cardio_minutes` | 分類後の運動時間 |
| `exercise_session_count` | セッション数 |
| `data_origin_summary` | 画面表示用の主な取得元 |
| `updated_at` | 最終集計時刻 |

### 8.2 `body_composition_daily`

| フィールド | 説明 |
|---|---|
| `date` | ローカル日付（主キー） |
| `weight_kg` | 体重 |
| `body_fat_percent` | 体脂肪率 |
| `fat_mass_kg` | 算出した体脂肪量 |
| `lean_body_mass_kg` | 取得値または推定値 |
| `lean_mass_source` | `health_connect` / `calculated` |
| `measurement_time` | 採用した測定時刻 |
| `data_origin` | 計測元 |

### 8.3 `weekly_analysis`

| フィールド | 説明 |
|---|---|
| `week_start` | 週の開始日（主キー） |
| `input_snapshot_json` | LLMへ渡した最小化済み入力 |
| `advice_json` | 構造化された助言結果 |
| `model_label` | 使用モデルの利用者向け表示名 |
| `generated_at` | 生成日時 |

### 8.4 `app_settings` / `sync_state`

- 目標（脂肪量・体重・歩数・筋トレ回数）、週の開始曜日、通知設定、選択したデータ提供元
- LLM有効化状態、モデル設定、暗号化済みAPIキーへの参照
- データ型ごとのHealth Connect変更トークン、最終同期時刻

## 9. 画面仕様

### 9.1 オンボーディング

1. アプリの目的と、端末内保存を説明する。
2. Health Connectの利用可否を確認し、利用不可なら必要な対応を案内する。
3. 利用したい指標を選択し、対応する最小権限を要求する。
4. LLM分析は任意であることを説明し、初期状態では無効にする。

### 9.2 ダッシュボード

- 今週の体脂肪量変化、除脂肪量変化、歩数平均、活動消費平均、筋トレ回数を優先表示する。
- 体重は補助指標として表示する。
- 各指標について、値、前週比、データ不足状態を表示する。
- 「同期」「今週を分析」操作を配置する。

### 9.3 体組成詳細

- 体重、体脂肪率、体脂肪量、除脂肪量を7日・28日範囲で折れ線表示する。
- 除脂肪量が計測値か算出値かを明示する。
- 単日の増減ではなく7日中央値を既定表示する。
- データ欠損日と、測定元・測定時刻を確認できる。

### 9.4 活動詳細

- 歩数、距離、活動消費カロリー、運動時間を日別棒グラフで表示する。
- 筋トレ・有酸素・その他の運動時間を週次集計で表示する。
- 運動セッション一覧では種目、時間、取得元を表示する。

### 9.5 週次アドバイス

- LLM未設定時は、端末内ルールで算出した数値サマリのみを表示する。
- LLM設定済み時のみ、「今週を分析」で外部LLMを呼び出す。
- 助言は「よかった変化」「注意点」「次の一手（最大3件）」「データの確からしさ」で構成する。
- 医療的な診断や断定をしない旨を常時明記する。

### 9.6 設定

- Health Connectの接続状態、同期のON/OFF、権限管理への遷移
- 目標設定、データ提供元の優先設定、通知設定
- LLMの有効化、APIキーの更新・削除、外部送信される項目のプレビュー
- アプリ内集計値・分析履歴の全削除

## 10. LLM連携

### 10.1 送信条件

- 利用者が「今週を分析」を押したとき。
- または、利用者が週次自動分析を明示的にONにした場合のみ。
- ネットワーク未接続・APIキー未設定・データ不足時は呼び出さない。

### 10.2 外部送信する入力

LLMへ渡すのは直近7日および比較対象の前週・28日トレンドであり、時系列の生データやHealth ConnectのレコードIDは渡さない。

```json
{
  "goal": "脂肪量を落とし、除脂肪量を維持する",
  "period": "直近7日",
  "body": {
    "fat_mass_7d_change_kg": -0.3,
    "lean_mass_7d_change_kg": 0.0,
    "weight_7d_change_kg": -0.3,
    "measurement_days": 6
  },
  "activity": {
    "steps_daily_avg": 7600,
    "active_calories_daily_avg": 430,
    "strength_training_sessions": 2,
    "strength_training_minutes": 90,
    "cardio_minutes": 95
  },
  "data_quality": {
    "body_composition_status": "sufficient",
    "activity_days": 7
  }
}
```

### 10.3 モデルへの指示と出力

- システム指示で、医療診断・疾病の推測・服薬や極端な食事制限の指示を禁止する。
- 数字の変化を単日で断定せず、測定日数やトレンドの確からしさを考慮させる。
- JSON Schemaに従い、次の構造で返す。

```json
{
  "summary": "一週間の総評",
  "positive_change": "継続できている点",
  "caution": "注意すべき点。なければnull",
  "next_actions": ["行動案1", "行動案2", "行動案3"],
  "confidence": "high | medium | low",
  "data_limitations": ["測定日数が少ない等"]
}
```

- APIキーはAndroid Keystoreで保護されたローカル領域にのみ保存する。
- アプリ内の分析履歴を削除した場合、入力サマリと助言結果も削除する。

## 11. 分析ルール（LLMなしでも実行）

| 条件 | 端末内の表示・助言方針 |
|---|---|
| 脂肪量が低下、除脂肪量が概ね維持 | 現在の食事・活動・筋トレを継続する成功パターンとして表示する。 |
| 体重横ばい、脂肪量低下、除脂肪量上昇または維持 | 体重だけで失敗と見なさず、体組成の改善として表示する。 |
| 脂肪量・除脂肪量がともに大きく低下 | 急な減量として注意表示し、睡眠・筋トレ・十分な栄養を確認するよう促す。診断はしない。 |
| 歩数または活動消費が前週より大きく低下 | 日常活動の低下として表示し、無理のない歩行機会の回復を提案する。 |
| 体組成の測定日が週3日未満 | トレンドの信頼度を低く表示し、可能なら同じ条件での測定継続を案内する。 |

## 12. プライバシーとセキュリティ

- アカウント、広告SDK、行動解析SDK、クラッシュレポートへの健康データ送信を導入しない。
- RoomのDBには集計値のみを保存し、Health Connectの生レコード、位置情報、心拍の連続時系列は保存しない。
- Android端末のバックアップからアプリDBおよびLLM APIキーを除外する。
- LLM利用時は、入力プレビュー、送信先、外部サービスのデータ取扱いを設定画面で確認可能にする。
- LLM APIを提供する事業者の利用規約・保存/学習方針は、利用者自身が設定時に確認する。
- 「Health Connect同期を停止」と「アプリ内データを削除」をいつでも実行可能にする。

## 13. 非機能要件

- 通常のダッシュボード表示はネットワーク未接続でも利用可能であること。
- 同期失敗時は既存のローカル集計を保持し、理由と再試行操作を表示すること。
- Health Connectの一部権限がない場合、他の許可済み機能は利用可能であること。
- LLM呼出し失敗時、健康データ・APIキー・助言履歴をログへ出力しないこと。
- 指標や取得元が欠損している場合、ゼロと誤認させず「未取得」と表示すること。

## 14. 受入条件

1. Health Connectが利用可能な端末で、必要な権限を許可するとダッシュボードに歩数・活動消費・運動時間が表示される。
2. 体重と体脂肪率が同時刻帯に存在すると、体脂肪量が正しく計算・表示される。
3. `LeanBodyMassRecord`がある場合、その値が除脂肪量として優先表示される。ない場合、算出値であることが明示される。
4. 歩数・距離・活動消費は日次集計として表示され、複数ソースの生レコードをアプリ側で単純加算しない。
5. 運動セッションが、筋トレ・有酸素・その他に分類され週次合計へ反映される。
6. アカウント作成なしで、すべての通常機能を利用できる。
7. LLM未設定でも、端末内のトレンドとルールベースの説明を利用できる。
8. LLM分析時に送信される内容をユーザーが確認でき、生ログ・記録ID・APIキーは送信されない。
9. アプリ内データ削除により、Room内の集計・設定・助言履歴・保存済みAPIキーが消去される。

## 15. 実装優先順位

1. Health Connect接続、権限、手動同期、日次集計
2. ダッシュボードと体組成・活動の詳細表示
3. Room永続化、日次WorkManager、データ品質表示
4. 端末内ルールベースの週次サマリ
5. BYOK方式のLLM連携、構造化出力、外部送信プレビュー
6. ローカル週次通知、取得元の詳細設定
